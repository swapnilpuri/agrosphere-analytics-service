`ProductionRevision` holds minimal validated collection facts, source identity/fingerprint and immutable attribution. A future parser validates the full collection-v2 schema and envelope/payload equivalence first. Its complete canonical-envelope fingerprint detects changed content even when the changed field is not a retained contribution fact. Fingerprint algorithm/parsing details still need concrete adapter review. No worker/actor/reason/measurement evidence is retained. REAL fixtures yield only minimal receipt/issue metadata and no collection contribution.

`ProductionProjection` is an immutable pure transition/rebuild model. Same event ID/fingerprint/identity is a no-op. Conflicts preserve current contributions and visible scoped issue evidence. Higher versions replace, lower versions only close observed holes, and void tombstones resist resurrection. Dates/timezones come from the producer snapshot; corrections can move collection date but cannot change estate/block/timezone. Per-block processing/source times and issue metadata prevent cross-estate activity leakage. Version-hole counts use arithmetic, not allocation proportional to version number. No raw envelope or former contribution archive is needed by this model.

Rebuild groups highest roots by snapshot collection date, uses exact BigDecimal sums of rounded producer dry mass, partitions wet mass and preserves pending versus measured zero. A day with no observed roots has null metrics. Void-only rows have zero active contribution and no known dry mass. Pending zero means DRC coverage of observed active roots only, never complete event history. Source references are capped at 100 per query and explicitly truncated; totals still cover all matching roots. Gaps/conflicts/unsupported metadata remain block-wide, not hidden by the date filter. No actual materialized table or source recovery guarantee exists yet.

`ReadProductionHistory` denies the proposed production-summary scope before reference or projection ports. `ProductionPorts` defines read/reference and atomic-commit expectations for future adapters. These are not signed-token verification, database transactions, ACK handling or external services. Port failures propagate; they do not become empty successful history.
